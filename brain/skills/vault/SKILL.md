---
name: vault
description: "Secrets vault for Brain — store/rotate/use/list API keys, tokens, passwords, credentials so the AI NEVER sees the value. Vault flow is s(target='vault_drop',...) → drop_url; the user pastes into a browser form, the server encrypts. NEVER ask the user to paste a value in chat. TRIGGER ON ANY MENTION OF: vault, secret, secrets, token, API key, password, credential, credentials, .env, save/store/add/rotate/use/list a key, 'my X token/key/secret/password'. Value injection (vault-run/vault-unlock) is local Claude Code only; catalog recall, value handles, and drop-URL flows work anywhere."

%bp2 vault|secrets
%tools b.r=recall(catalog + value-handle) b.s=store(vault_drop) · bin: vault-run(inject value into one Bash cmd) vault-unlock(prints a code + opens the portal approval page → opens this CC session per the user's own vault security setting) vault-resolve vault-put(store a secret that is already in a local file, without a paste form)
%req Depends on the Brain MCP server (tools r/s) and the brain plugin's bin scripts. Catalog recall, the value handle, and drop_url relay work in any host (Claude Code, web, SDK). Resolving a handle to a VALUE — vault-run/vault-unlock — is local Claude Code ONLY; on web/SDK there are no local binaries and the portal step-up cannot substitute (it elevates the portal session, not the MCP client's token), so say so plainly rather than sending the user round a step-up loop. Vault is alpha; if the backend is unreachable, say so plainly and continue without it.
%rule Brain-first still applies: r(namespace="<user>:vault", query) before assuming a secret isn't stored. r(namespace="<user>:vault") returns CATALOG ONLY (episode_id, env_var, purpose, related). The server holds encrypted values: legacy entries under the user's Keycloak vault_dk, or — once the user enrols vault keys — sealed to their vault public key, openable only while the vault key is unlocked in the portal (passkey/recovery key). A fresh MFA step-up at the level the user's vault policy names (loa2 = WebAuthn second factor; loa1 = password-only policy) gates all value access either way. The catalog (episode_id, env_var, username, purpose) is never encrypted. Use natural language; never ask the user to type episode_ids or paste values in chat.
%rule FORBIDDEN: NEVER ask the user to paste a secret/key/token/password value in chat. NEVER offer "paste it anyway, I'll store it" or "store a placeholder" as options. NEVER ask clarifying Qs when the service name is clear ("test key for test service" → episode_id="secret:test:test", env_var="TEST_TEST", just fire the drop). The ONLY correct path for any "save/store/add/rotate my X" request is s(target="vault_drop",...) → relay drop_url — EXCEPT when the secret already sits in a file on this machine (local CC): then use `vault-put --file`, never a drop (see Patterns). The AI must never see the value: NEVER cat/read/base64/echo the file or pipe it anywhere visible; pass its path to vault-put.
%rule Patterns:
  • "save/store/add my X [token|secret|key|password]" → infer episode_id from convention, then s(namespace="<user>:vault", target="vault_drop", data={episode_id, env_var, purpose, value_type?, username?}) which returns {drop_url, expires_in}. username = the account the secret belongs to (login/email/client id) — it is plaintext catalog data, so pass it when known; never put a secret in it. Relay the URL to the user WITH the deadline in human terms (expires_in is seconds; default 600 → "open within 10 minutes — it may ask you to sign in / MFA first"). They open it in a browser, paste the value into the server-hosted form, the server encrypts + stores. The AI never sees the value. If the user reports the link expired or 404'd, mint a fresh slot with the SAME data immediately — no questions, no apology tour; add ttl (seconds, max 1800) to data if they need a longer window.
  • "rotate my X" → same s(target="vault_drop", data={episode_id, env_var, ..., overwrite:true}). The drop form replaces the existing value on submit.
  • "back up / store secrets/ota.key" (secret is a FILE on this machine, local CC) → Bash `vault-put <episode_id> --env-var <VAR> --type <type> --file <path> [--base64] [--purpose "..."] [--username <acct>]`. Pass --base64 for anything binary (keys, certs, keystores); text tokens go without it. It prints catalog metadata only and Brain writes the catalog, so r() finds it. Writes need FRESH MFA — a session grant covers reads only — so if vault-put exits 2 tell the user to run `vault-unlock --force`, then re-run the SAME vault-put. It refuses to overwrite: add --rotate to replace (pass --purpose again, or the catalog keeps the old one). Restore a --base64 entry with `vault-run <id> -- sh -c 'printf %s "$VAR" | base64 -d > <path>'`.
  • "use my X [for Y]" / "with my X token" → r(namespace="<user>:vault", query="X") to find episode_id, then r(namespace="<user>:vault", episode_id="<found>") for the invocation hint. That call returns status="ready" with env_var + invocation.local_plugin shape (e.g. `vault-run secret:hf:token -- <cmd using $HF_TOKEN>`) — run it in Bash (local CC). The handle is catalog-grade and NOT step-up gated: it carries no secret, so it never returns step_up_required. MFA is enforced one step later, by vault-run. If vault-run reports stale MFA, tell the user to run `vault-unlock` and then re-run the SAME vault-run command — do not re-call r(), nothing about the handle changed. The value never appears in any r() response; vault-run is the only path that touches plaintext and it redacts child stdout/stderr. NEVER inline `<<vault:...>>` in commands (PreToolUse blocks it).
  • "what's in my vault" / "list my secrets" → r(namespace="<user>:vault") — returns the catalog. No values.
  • "who accessed X" / "vault activity" → r(namespace="<user>:vault", query="X", mode="chronological") — audit trail.
  Confirm names only when ambiguous. Otherwise infer and proceed.
%rule Naming: episode_id = `secret:<service>:<purpose-or-key>` (e.g. `secret:github:token`, `secret:openai:api-key`, `secret:keycloak:cloudflare-access:amnesia-labs`). env_var = `<SERVICE>_<TYPE>` uppercase (`GH_TOKEN`, `OPENAI_API_KEY`, `KEYCLOAK_CLIENT_SECRET`). value_type ∈ token|password|client_secret|api_key|private_key.
%rule Catalog text shape: when a vault catalog episode is written (either by drop_submit server-side, or by the AI describing a credential in `<user>:vault`), lead the `text` with the searchable identifiers as bare tokens — split the colon-delimited episode_id into segments, then env_var, then value_type — and append any purpose/free-text last. Example: `text="secret github token GH_TOKEN token GitHub PAT for CI"` rather than `"The GitHub PAT — injected as $GH_TOKEN for CI"`. Single-keyword recall ("github", "GH_TOKEN", "token") cosine-matches the keyword head where prose connectors bury those terms.

That tap signs in at the level THEIR vault policy names and, on a realm with the brain-vault login theme and a linked key, also unlocks the vault key; vault-run then opens this session's grant and carries on with the same command. No code, no portal page, no separate vault-unlock step. A cold start (no Keycloak session) asks the password once first. If the vault key is still locked after the tap (no key linked yet), vault-run opens the portal unlock page as a fallback. Inside CC one unlock opens a grant for THIS session for the policy's window: vault-run keeps working until it lapses or the session ends (SessionEnd closes it), so never re-unlock "to be safe" and never pre-fetch values into env vars — call vault-run per command. If it timed out, re-run the SAME command. Do not re-call r() or mint a drop.

%api
r(namespace="<user>:vault", query | episode_id, mode="auto"|"chronological")
Value-handle path: when namespace is a vault namespace and episode_id is set, r() returns {status:"ready", env_var, value_type, invocation} or {status:"not_found"}. **The value is never returned** — invocation.local_plugin points the AI at vault-run. Catalog-grade and NOT step-up gated: it exposes exactly what /vault/list already does, so there is no step_up_required and no escalation_url on this path. The step-up is enforced by vault-run's own call to /vault/value/get, which is where plaintext is actually released.
s(namespace="<user>:vault", target="vault_drop", data={episode_id, env_var, purpose, value_type?, username?, overwrite?}) → {drop_url, expires_in}
bin: vault-put <episode_id> --env-var NAME (--file PATH | --stdin) [--type token|password|api_key|private_key|client_secret] [--username ACCT] [--purpose TEXT] [--base64] [--rotate] [--namespace NS] → prints catalog metadata JSON; exit 2 = needs `vault-unlock --force`; value never accepted in argv
